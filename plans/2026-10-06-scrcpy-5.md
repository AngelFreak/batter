## What and why

scrcpy 5.0 was released 2026-10-05 (4.0 on 2026-05-12, 4.1 on 2026-07-12). Batter
pins 3.3.4. We only use **scrcpy-server** (the jar pushed to each phone). Our own Go
backend speaks scrcpy's wire protocol and the browser decodes the stream. That makes
upstream's desktop-client headlines irrelevant to us (SDL3, hardware decoding on the
PC, window aspect lock). Several **server-side wire-protocol changes in 4.0** do
affect us. **A version-string bump alone would break every device session.** The
server also refuses a client whose version string differs from its own, so the bump
and the protocol changes have to ship together.

Server-side changes that matter to us (checked against upstream source at tags `v3.3.4` and `v5.0`:
`Streamer.java`, `Options.java`, `ControlMessage*.java`, `doc/develop.md`):

1. **Video stream header shrinks.** v3 sent `name(64) + codec(4) + width(4) +
   height(4)` = 76 bytes. 4.0+ sends `name(64) + codec(4)` = 68 bytes. Width and height
   move into a new **session packet**.
2. **New session packet** (12 bytes, video only): `u32 flags` (bit 31 set = session
   packet; bit 0 = "client resized", flex display only), then `u32 width` and `u32 height`.
   One is sent before the first media packet and again **for every capture session.
   A session changes when the device rotates.** It has the same length as a frame
   header but carries no payload.
3. **Frame-header flag bits shift down by one, on video *and* audio**, because
   `Streamer` is shared. Bit 63 = session (was config), bit 62 = config (was key
   frame), bit 61 = key frame. PTS is now the low 61 bits (was 62).
4. Server option `send_codec_meta` is renamed `send_stream_meta`. We don't pass it;
   the default (true) is what we need.
5. New control types 18–22 (camera torch/zoom, resize display, scan file). These are
   additive. Our encoded types 0–11 and their layouts are unchanged (verified by diffing
   `ControlMessageReader.java`). Device→client messages (`DeviceMessage.java`) are
   unchanged.
6. Behavioural changes in the server that we inherit: "optimal size alignment"
   (#6746) can change the encoded size by a few pixels compared with `max_size`. The
   encoder runs with minimum `KEY_PRIORITY`/`KEY_LATENCY` (#6670). Encoder size
   constraints are respected after a first failure (4.1). Audio playback capture
   now takes all usages (5.0, #6975), so phone audio may include sounds it used to drop.

## Approach

### Backend (Go)

- `internal/device/scrcpy.go`: read the 68-byte header. Then read exactly one
  12-byte packet, require the session flag, and take the initial `Width`/`Height` from
  it. Fail the session with a clear error if the first packet isn't a session
  packet, because that means the server version doesn't match the expected protocol.
- `videoReadLoop`: when a header has bit 63 set, treat it as a session packet with
  **no payload**. Don't read `size` bytes. Update the session's size and don't broadcast
  it to viewers. Config/key checks move to bits 62/61. The stored config packet is
  keyed on bit 62.
- **Width/Height become mutable**, guarded by a mutex or stored as an atomic pair behind
  a `Size()` accessor. `device_ws.go` currently snapshots `session.Width/Height` once
  per control connection, so after a rotation touches are encoded with stale dimensions,
  and the server **silently drops** touch/scroll events whose size doesn't match.
  `device_ws.go` will read `Size()` per message. This fixes a rotation bug we already
  have, and v5's session packet is what makes the fix possible. The `devices.go`
  JSON responses use `Size()`.
- `videosub.go` `packetFlags`: config = `0x40`, key = `0x20` on byte 0.
- `scrcpy_audio.go`: config check moves to bit 62. Audio has no session packets, so
  bit 63 on audio is a protocol error. Log it and end the audio stream.
- Centralise the bit positions as named constants in `protocol.go`
  (`packetFlagSession/Config/KeyFrame`, `ptsMask`) so the Go readers can't drift
  apart again.
- `internal/device/scrcpytest` (the fake server): emit the v5 framing, including
  a session packet at start and on simulated rotation.
- `manager.go`: drop the stale `"2.7"` fallback and default to the config value,
  so there's a single source of the version.

### Browser

- `web/src/lib/device-video.ts`, `device-video-thumbnail.ts`, `device-audio.ts`:
  config = `(ptsHigh >>> 30) & 1`, key = `(ptsHigh >>> 29) & 1`, and the PTS mask becomes
  `0x1fffffff`. Session packets never reach the browser (the backend consumes them),
  but each parser drops a packet with bit 31 set defensively, rather than decoding it
  as media. The decoding moves into one shared helper (`scrcpy-packet.ts`) used by all
  three, matching the Go change.

### Version pin and supply chain

- `SCRCPY_VERSION` 3.3.4 → **5.0** in `Dockerfile`, `internal/config/config.go`,
  `.env.example`, `README.md`, `scripts/install-scrcpy.sh`. Upstream dropped the
  patch component, so the tag is `v5.0` and the asset is `scrcpy-server-v5.0`. The URL
  pattern still holds.
- **Add SHA-256 verification** of the downloaded server in the `Dockerfile` (it's
  fetched today with no integrity check):
  `26cbc9ad0aced6c2282455bef4fb43462605c1f8758c74b4ab1dbf818c229daa` (from the
  GitHub release asset digest, to be cross-checked against upstream's signed
  `SHA256SUMS.txt.asc` before merging). Do the same in `install-scrcpy.sh`.
- `install-scrcpy.sh`: its version probe `grep -oP '\d+\.\d+\.\d+'` doesn't match
  `5.0`, so it would reinstall every run. Accept an optional patch component.
- Dependency flag (§3.5): same dependency (Genymobile/scrcpy, Apache-2.0, French
  OSS vendor), new major version. It's a jar executed on our phones, so it gets hash
  pinning as above. No new dependency.

## Risks

- **All device sessions break if any one parser is missed.** That's mitigated by the
  shared constants/helper, by the fake server emitting v5 framing, and by a repo-wide
  grep for `>> 63`, `>>> 31`, `0x80`, `0x3fffffff` before merging.
- **Mixed versions:** the server version check means an old image with a new jar (or
  the reverse) fails loudly at start rather than misparsing. That's acceptable and
  intended. A jar left on a phone from an earlier run is overwritten on every session
  start (`adb push`).
- **Rotation mid-session** now changes the reported size. Viewers already reconfigure from
  the new SPS. Touch mapping uses normalized coordinates × current size, so this is a fix.
- **Size alignment** may change the stream size slightly (e.g. 1024 → 1024 or 1016).
  The browser takes its size from SPS, and touch uses the session packet's size, so both
  stay consistent.
- **Old Android versions:** confirm scrcpy 5.0's minimum Android API is still ≤ the
  oldest phone we have attached before deploying.
- Audio now captures every usage on the phone. That's a behaviour change for listeners,
  not a protocol one. It goes in the deploy notes.

## Tests (§7 — evidence, not descriptions)

Go (against the real readers, fed by `scrcpytest` v5 framing):
- Handshake: a 68-byte header plus a session packet `1080×2400` gives
  `Size() == (1080,2400)`. If the first packet is a media header (bit 63 clear), the
  session errors with "unexpected first video packet".
- Rotation: a session packet `2400×1080` mid-stream updates `Size()`. The next touch
  control message encodes `w=2400,h=1080`; the test asserts on the bytes written to
  the control socket. No viewer channel receives the session packet.
- Flags: a config packet (bit 62) is stored and replayed to a late subscriber. A
  keyframe (bit 61) clears `videoSub.resync`. A delta with bit 61 clear is dropped
  while resyncing.
- Audio: the config packet (bit 62) is stored as `audioConfig`. A packet with bit 63
  ends the stream with a logged error.
- **Mutation check:** reverting any one of the bit constants to the v3 value must
  fail at least one test. I'll do this by hand and record it in progress.

Browser (`npm test`: tsc + `node --test`, as the repo already uses):
- `scrcpy-packet.ts`: the header decode table for session/config/key/delta and the
  PTS mask, with a value that has bit 61 set, so a v3-style mask would fail.
